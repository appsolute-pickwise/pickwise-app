# 상품 정보 관리

## 목적과 범위

JSON이나 DB 테이블을 직접 편집하지 않고 Flutter 앱에서 상품·가격·출처·사양을 등록하고 수정한다. 기존 색상·로고·Provider 구조와 제품 조회 API를 유지한다. 가격 이력 그래프·목표가 알림·제품 삭제·사진 업로드·다른 제품군 지원은 이번 범위가 아니다.

## 앱 사용 방법

1. 관리자 권한이 부여된 기존 PickWise 계정으로 로그인한다. 이미 로그인 중이었다면 Hot Restart 또는 앱 재실행으로 서버의 계정 권한을 다시 확인한다.
2. 마이페이지 → **상품 관리**로 이동한다. 일반 계정에는 이 메뉴가 표시되지 않는다.
3. 제품을 선택하면 서버의 최신 정보와 버전을 불러온다. **상품 등록**으로 새 이어폰을 추가할 수 있다.
4. 브랜드·제품명·원화 가격·가격 확인일·출처 링크·용도 태그를 입력한다. 제품 ID는 영문 소문자·숫자·하이픈으로 만들며 등록 후에는 바꾸지 않는다.
5. 사진은 현재 앱에 포함된 제품 사진 중 선택하거나 ‘사진 없음’을 사용한다. 새 사진 파일을 업로드하는 기능은 없다. 새 자산이 필요하면 앱 자산에 추가하고 앱을 다시 빌드해야 한다.
6. **사양 추가**에서 착용 형태, ANC 지원, 배터리, 무게, 방수 등급 등을 추가한다. 배터리는 이어버드·케이스 포함 여부와 ANC 켬·일반 재생을 분리한다.
7. 사양별 출처 URL과 확인일은 함께 입력하거나 둘 다 생략한다. 날짜는 `YYYY-MM-DD` 형식이며 미래 날짜는 서버에서 거부한다.
8. **상품 정보 저장**을 누른다. 성공하면 관리 목록과 앱 카탈로그를 다시 받아 탐색·추천·비교에 반영한다.
9. 상품 수정 화면의 **변경 기록**에서 최근 관리자 등록·수정 기록을 확인한다.

입력 폼은 스크롤 밖의 필수 항목도 모두 검증한다. 저장 중에는 중복 저장·추가 편집을 막는다. 작성 중 뒤로 가거나 서버 정보를 다시 불러오면 저장하지 않은 내용을 버릴지 확인한다. 저장 결과가 불명확한 통신 장애에서는 자동 재전송하지 않고 목록에서 실제 저장 여부를 먼저 확인하도록 안내한다.

## 수동 가격과 자동 가격 갱신

제품별 **가격 자동 갱신** 스위치가 있다. 새 상품은 기본 비활성이며 기존 카탈로그는 기존 자동 갱신 동작을 유지한다.

- 자동 갱신은 현재 다나와 제품별 링크만 지원한다. 네이버·에누리 출처는 수동 가격으로 관리한다.
- 수동 가격을 계속 유지하려면 스위치를 끈다.
- 스위치를 켜면 다음 정규 조회에서 확인한 가격으로 바뀔 수 있다. 수동 가격·출처·확인일 변경 후에는 그 시점부터 최소 1시간 간격을 적용한다.
- 가격·가격 출처·가격 확인일을 수정하면 `priceFetchedAt`을 비우고 `manual` 상태로 바꾼다. 관리자가 입력한 값을 외부 자동 조회 값으로 표시하지 않는다.
- 브랜드·사양만 수정했다면 기존 가격 조회 메타데이터는 유지한다.
- 관리자 수정 중 도착한 이전 자동 수집 응답은 제품 버전·출처·자동 갱신 허용 여부가 일치할 때만 반영한다.

공개 페이지 기반 가격 조회의 한계와 이용 조건은 [가격 자동 갱신 문서](가격_자동_갱신.md)를 따른다.

## 권한 부여와 회수

회원가입·일반 프로필 API로는 관리자 권한을 얻을 수 없다. 기존 계정의 DB 권한을 서버 운영자가 별도로 설정한다. 관리자 이메일을 소스 코드에 하드코딩하지 않았다.

로컬 개발 환경의 기존 계정에만 사용하는 도구:

```bash
python3 backend/scripts/admin_access.py grant manager@example.test
python3 backend/scripts/admin_access.py revoke manager@example.test
```

계정이 없으면 실패하며 임의 비밀번호나 계정을 만들지 않는다. 입력 이메일은 UTF-8 hex literal로 전달하여 SQL 문자열에 원문을 삽입하지 않는다. 비밀번호·접근 토큰은 명령 인자로 받거나 출력하지 않는다. 이 도구는 현재 개발용 Docker Compose 전용이며 공개된 권한 변경 API가 아니다.

이번 작업에서 사용자가 지정한 기존 계정 하나에 관리자 권한을 부여했다. 실제 이메일은 이 문서에 저장하지 않는다.

`GET /api/v1/auth/me`의 `admin` 값은 서버 DB에서 확인한다. 앱은 저장소의 임의 권한 값을 신뢰하지 않고 서버 확인 후에만 메뉴를 표시한다. 로그아웃·계정 전환 시 메모리의 관리자 상태를 비운다. 화면이 열려 있는 동안 계정이 바뀌면 해당 화면의 응답을 무효화한다. 권한을 회수하면 기존 토큰이 남아 있어도 서버의 관리자 요청은 403으로 차단된다.

## API 계약

| 경로 | 기능 |
|---|---|
| `POST /api/v1/admin/products` | 상품 등록. 입력 version은 0 |
| `GET /api/v1/admin/products/{id}` | 편집할 최신 상품·버전 조회 |
| `PUT /api/v1/admin/products/{id}` | 상품 전체 수정. 본문의 ID와 경로 ID가 일치해야 함 |
| `GET /api/v1/admin/products/{id}/changes` | 최근 관리자 변경 기록 최대 20개 |

모두 유효한 Bearer 세션과 서버의 관리자 권한이 필요하다. 세션 없음·만료는 401, 관리자 권한 없음은 403, 없는 제품은 404, 중복 ID·수정 충돌은 409이다. 스키마는 `backend/openapi.yaml`을 따른다.

입력 검증:

- 양의 정수 가격, 과도하게 긴 문자열, 중복 태그·중복 사양 키를 검증한다.
- 숫자 배터리·무게와 단위, boolean ANC·귀걸이형 고정 구조를 구분한다. 누락 사양을 임의의 수치나 false로 채우지 않는다.
- 가격 출처는 선택한 사이트의 허용 도메인인지 확인한다. 다나와는 제품 번호가 포함된 고정 상품 URL 형식만 허용한다.
- 사양 출처는 HTTPS URL만 저장한다. 서버가 임의의 출처 URL을 조회하지는 않는다.
- 로컬 이미지 경로는 제품 자산 영역과 허용 확장자로 제한한다. 잘못된 사진은 앱의 기존 대체 이미지로 표시한다.

## 데이터 보존과 충돌 처리

`V5__catalog_management.sql`은 기존 사용자의 `is_admin=false`, 제품의 `version=0`, 기존 제품의 `price_auto_refresh=true`와 관리자 변경 이력 테이블을 추가한다. 기존 V1~V4는 수정하지 않는다. 계정·상품·비교 기록을 초기화하지 않는다.

관리자 등록·수정과 변경 기록은 한 트랜잭션으로 저장한다. 수정 시 사용자 권한과 제품 행을 잠그고, READ COMMITTED에서 최신 정보를 확인하며 최종 UPDATE에도 버전 조건을 둔다. 두 관리 화면에서 같은 버전으로 저장하면 하나만 성공하고 다른 하나는 409가 된다. 화면 입력은 유지하며 최신 정보 다시 불러오기는 사용자가 명시적으로 선택한다.

변경 기록에는 작업 계정 ID·시각·동작·수정 전후 제품 정보를 보관한다. 계정 비밀번호·세션 토큰은 기록하지 않는다. 앱에서는 제품 정보와 시각을 표시한다. 자동 가격 수집은 관리자 변경 기록에 넣지 않으며, 가격 이력 그래프를 위한 별도 기록은 다음 단계이다.

현재 제품이 수정되어도 이미 저장된 비교의 스냅샷은 바꾸지 않는다. 제품 ID는 수정하거나 재사용하지 않으며 삭제 API도 추가하지 않았다.

## 검증

서버 전체 테스트 29개가 통과했다. 실제 MySQL을 사용하며 외부 가격 페이지를 테스트 중 무작위로 호출하지 않는다.

- 실제 MySQL 테스트 DB에서 관리자·일반 사용자·권한 회수, 등록·수정·중복 ID·입력 오류·수정 충돌·이력·기존 스냅샷 보존을 검증했다.
- 가격 수집 응답이 도착하기 전에 관리자가 수정한 상황에서 과거 응답이 수동 가격을 덮어쓰지 않는지 검증했다.
- 실제 동시 요청 테스트에서 같은 버전의 저장 요청 중 하나는 성공하고 하나는 409가 되는지 확인했다.
- 격리된 8081 Docker API와 `pickwise_test` DB에서 실제 HTTP 회원가입·로그인·관리자 등록·수정·403·409·권한 회수·스냅샷 보존이 통과했다. 이 검증에서 만든 테스트 계정·상품·기록과 임시 컨테이너만 정리했다.
- Flutter 관리자 화면 테스트 9개가 통과했다. 일반 계정 메뉴 숨김·직접 진입 차단, 등록·수정, 충돌 시 입력 보존, 스크롤 밖 입력 검증, 작은 화면과 2배 글자, 로그아웃을 포함한다.
- Flutter 전체 회귀 테스트 179개 통과. 기존 `LIVE_API_URL` 조건의 실제 서버 테스트 4개는 기본 실행에서 제외된다.
- Flutter 정적 분석 오류 없음. Android 디버그 APK 빌드 성공.
- 8080 API 적용 전후에 MySQL 컨테이너 ID, 계정·상품·비교 기록 수, 비교 스냅샷 해시를 대조하여 보존을 확인했다.

시뮬레이터 화면 직접 조작은 하지 않았다. 사용자는 앱 재실행 후 관리자 마이페이지에서 등록·수정을 확인할 수 있다. Git 커밋·푸시·브랜치 변경은 수행하지 않았다.
