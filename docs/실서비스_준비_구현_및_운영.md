# PickWise 실서비스 준비 — 구현 결과와 배포 전 절차

2026-11-15 기준이다. 공개 배포를 실행하지 않았으며, 현재 Mac의 개발 Docker만 사용한다. 기존 색상·로고·Provider와 MySQL 볼륨을 유지했다.

## 구현한 기능

### 비밀번호 변경

마이페이지 → 비밀번호 변경에서 현재 비밀번호·새 비밀번호·확인을 입력한다. 8~128자 정책은 유지하고 문자 종류 조건은 추가하지 않았다.

`PUT /api/v1/me/password` 요청은 `currentPassword`, `newPassword`를 포함한다. 서버는 유효한 세션과 현재 비밀번호를 다시 확인하고 새 무작위 salt로 해시를 만든다. 변경과 모든 접근·갱신 세션 삭제를 한 트랜잭션으로 처리한다. 다른 기기도 다시 로그인해야 한다.

잘못된 현재 비밀번호는 422이며 기존 로그인은 유지한다. 성공은 204이며 앱 보안 저장소도 정리한다. 응답이 불명확한 변경 요청은 자동 재전송하지 않는다. 로그인·갱신·변경이 충돌할 때 사용자 행을 먼저 잠가 이전 비밀번호로 만든 세션이 변경 이후 남는 경합을 줄였다.

### 운영 요청 보호

`production` 프로필에 다음 필터를 적용한다.

- 동일 IP의 로그인·가입: 합산 분당 20회
- 갱신: 분당 60회
- 비밀번호 변경: 분당 5회
- 초과: 429와 `Retry-After: 60`
- 인증·개인 API: `Cache-Control: no-store`
- 콘텐츠 유형 추측·프레임 삽입을 제한하는 응답 헤더
- 잘못된 JSON·입력 검증에 비밀번호 원문을 포함하지 않는 오류 응답

제한 저장소는 인스턴스 메모리이며 최대 10,000개 키를 유지한다. 재시작하면 초기화된다. 단일 인스턴스 보호이며 분산 공격·계정별 공격 방어를 완성한 것은 아니다. 여러 API 인스턴스로 늘리기 전에 게이트웨이/공유 저장소 기반 제한으로 옮겨야 한다. 같은 공용 IP를 쓰는 이용자는 제한을 공유하므로 실제 이용 규모에 맞춰 조정해야 한다.

기본적으로 클라이언트가 보낸 IP 헤더를 신뢰하지 않는다. 준비한 운영 구성에서만 프록시의 `X-Real-IP`를 사용한다. 프록시가 이 헤더를 실제 연결 IP로 덮어쓰며 API 포트를 외부에 공개하지 않는 구조를 유지해야 한다.

## 운영 환경 구성

개발용 `backend/compose.yaml`은 유지했다. 운영은 **별도** `backend/compose.production.yaml`을 사용하며 프로젝트와 데이터 볼륨도 분리했다. 두 파일을 합쳐 실행하지 않는다.

| 구성 | 준비 내용 |
| --- | --- |
| MySQL 8.4 | 외부 포트 없음, 별도 영구 볼륨, 비밀 파일로 사용자·root 비밀번호 입력 |
| Spring Boot | 외부 포트 없음, 비루트 사용자, 읽기 전용 파일시스템, `/tmp`만 임시 쓰기 |
| 자원 제한 | API 메모리·프로세스·Tomcat 동시 처리 수 제한 |
| Nginx | 80→HTTPS 이동, TLS 1.2/1.3, 요청 본문 최대 16KB, IP별 일반 요청 제한 |
| 로그 | 컨테이너 로그 파일 크기·개수 제한, 프록시 로그에서 쿼리·본문·인증 헤더 제외 |
| 비밀 자료 | `deploy/secrets`, `deploy/tls`, `.env.*`, 백업은 Git 제외 |
| 앱 릴리스 | HTTPS API 주소 미지정 또는 HTTP 주소 사용 시 시작을 차단. 디버그 기본 주소는 유지 |

도메인과 실제 인증서는 아직 없다. TLS 파일 준비·갱신은 자동화하지 않았고 실제 공개 HTTPS 연결도 검증하지 않았다. 이 상태를 공개 배포 완료라고 보지 않는다.

### 향후 운영자 준비 명령 — 이번에는 실행하지 않음

서버·도메인과 인증서 발급 방법을 결정한 뒤 `backend` 디렉터리에서 진행한다.

```bash
cp .env.production.example .env.production
# .env.production의 PICKWISE_DOMAIN을 실제 API 도메인으로 수정
umask 077
mkdir -p deploy/secrets deploy/tls
chmod 700 deploy/secrets deploy/tls
openssl rand -hex 32 > deploy/secrets/db_password
openssl rand -hex 32 > deploy/secrets/db_root_password
# Compose 파일 기반 secret은 호스트 소유권을 유지할 수 있어 비루트 API 읽기 권한이 필요
# 호스트의 다른 사용자는 상위 700 디렉터리를 통과할 수 없음
chmod 444 deploy/secrets/db_password
# 발급한 인증서: deploy/tls/fullchain.pem
# 발급한 개인 키: deploy/tls/privkey.pem
# 인증서 갱신·프록시 reload 작업도 운영 환경에서 구성

docker compose --env-file .env.production -f compose.production.yaml config --quiet
# 위 파일·도메인·방화벽·인증서·백업이 준비된 이후에만:
# docker compose --env-file .env.production -f compose.production.yaml up -d --build
```

Compose의 파일 기반 secret은 소유권·mode 재지정이 환경에 따라 적용되지 않을 수 있다. 위처럼 상위 디렉터리는 700, API가 읽는 파일은 읽기 가능하게 준비하고 실제 서버에서 비루트 API의 secret 읽기를 확인한다. 전체 운영 스택 기동은 아직 검증하지 않았다.

비밀번호 파일은 최초에만 만들고 기존 DB에 연결된 값을 덮어쓰지 않는다. 데이터베이스 비밀번호 변경은 DB 사용자 설정과 함께 별도 절차로 진행한다. 운영 볼륨을 삭제하는 명령을 일반 종료에 사용하지 않는다.

앱 릴리스 주소는 다음처럼 지정한다. 실제 릴리스 서명·스토어 제출은 하지 않았다.

```bash
flutter build appbundle --dart-define=PICKWISE_API_URL=https://실제-API-도메인
```

## 백업·복구

`backend/scripts/backup.sh`는 운영 스택의 일관된 MySQL 덤프를 `backups`에 권한을 제한해 저장한다. 완료 전 파일은 `.partial`이며 실패하면 정리한다. 같은 파일을 덮어쓰지 않는다.

운영 스택이 실행된 이후, `backend`에서 도메인 환경을 불러오고 실행한다.

```bash
set -a
. ./.env.production
set +a
sh scripts/backup.sh
sh scripts/restore-check.sh backups/검증할-백업.sql
```

복구 검증 스크립트는 **외부 포트·네트워크가 없는 임시 MySQL**에 복원한다. 최소 스키마를 검사하고 임시 컨테이너·자격 파일을 정리한다. 현재 개발 DB나 운영 DB를 덮어쓰지 않는다.

이번에는 `pickwise_test` DB 덤프를 별도 컨테이너에 복원해 8개 테이블의 복구를 확인했다. 실제 운영 데이터의 장기 보관·외부 암호화 백업·자동 예약·보존 기간은 아직 설정하지 않았다. 이 스크립트는 그 정책 자체를 대신하지 않는다.

## 자동 검증

`.github/workflows/verify.yml`을 추가했다. PR 또는 main 반영 시 다음을 실행하도록 준비했다.

- Flutter 포맷·분석·전체 테스트·Android 디버그 빌드
- Java 21과 별도 MySQL 8.4에서 서버 테스트
- 저장소 읽기 권한만 사용. 배포·PR 생성·병합 작업 없음

로컬 SDK에 맞춰 Flutter 3.47.1을 지정했다. 이 환경에서 공식 Linux 릴리스 메타데이터 조회가 HTTP 404를 반환해 다운로드 가능 여부를 검증하지 못했다. GitHub Actions는 아직 실행되지 않았다. 사용자가 저장소에 반영한 후 첫 실행에서 설치와 실행 결과를 확인해야 한다.

## 이번 검증 결과

| 검증 | 결과 |
| --- | --- |
| `flutter analyze` | 오류·경고 없음 |
| Flutter 전체 | 실제 로컬 Docker HTTP 포함 96개 통과 |
| 서버 | 실제 MySQL 통합 및 요청 필터 테스트 총 13개, 실패 0 |
| 비밀번호 변경 실제 HTTP | 잘못된 현재 비밀번호의 세션 유지, 변경 후 이전 세션 폐기, 새 로그인 확인 |
| 로컬 API 응답 | 401 및 no-store·보안 헤더 확인 |
| 운영 Compose | 별도 도메인 자리표시자로 구문 검사 통과, 운영 스택 미실행 |
| Nginx | 자체 서명 임시 인증서·테스트용 upstream으로 `nginx -t` 통과, 실제 도메인 연결 아님 |
| 복구 검사 | 테스트 DB 덤프를 격리 MySQL로 복원, 8개 테이블 확인 |
| 빌드 | Android APK·iOS 시뮬레이터용 앱 컴파일 성공 |

시뮬레이터를 직접 제어하지 않았다. 실제 OS 보안 저장소·기기 재실행·공개 네트워크는 별도 확인 대상이다. 커밋·푸시·PR 생성은 하지 않았다.
