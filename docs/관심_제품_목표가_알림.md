# 관심 제품과 목표가 알림

작성일: 2026-11-17

## 구현 범위

제품 상세에서 로그인한 사용자가 관심 제품과 목표 가격을 저장한다. 마이페이지의 **관심 제품**에서 수정·해제하고 **가격 알림함**에서 도달 기록을 확인한다. 기존 색상·로고·Provider 구조는 유지했다.

목표 가격을 비우면 관심 제품만 저장한다. 입력 시 1~2,147,483,647원의 정수만 허용한다. 계정당 관심 제품은 최대 100개다. 목표가는 저장 후 새로 정상 조회한 자동 가격에 대해서만 평가한다. 저장 전에 이미 표시하던 가격이나 관리자의 수동 가격 입력으로 즉시 알림을 만들지 않는다.

자동 가격이 목표가 이하이면 해당 설정 버전에 한 번 알린다. 가격이 오르내려도 같은 설정으로 반복 알리지 않는다. 다시 받으려면 **목표가 수정 · 다시 알림**에서 명시적으로 저장한다. 설정 이후 출처가 바뀌면 알림 평가를 중단하고 목록에 안내한다. 새 출처를 확인한 뒤 다시 저장해야 한다.

## 화면 사용 방법

1. 평소처럼 `main.dart`를 실행하고 로그인한다. 별도 실행 인자는 필요 없다.
2. 제품 상세 → **관심 제품 · 목표가 설정**을 선택한다.
3. 목표 가격을 입력하고 저장한다. 관심 저장만 원하면 비워둔다.
4. 마이페이지 → **관심 제품**에서 등록 결과와 알림 대기 상태를 확인한다.
5. 해당 제품의 정상 자동 조회가 목표가를 만족하면 **가격 알림함**에 기록된다.
6. 관심 해제 후에도 이전 알림은 조회 당시 스냅샷으로 남는다.

개발용 자동 조회는 제품별 최소 1시간 간격이다. 앱 알림함을 열어두면 30초 간격으로 갱신하며 당겨서 새로고침할 수 있다. 가격 자동 조회를 끄면 새 가격 기반 알림도 생성되지 않는다. 표시 가격은 마지막 관측 가격이고 최종 결제 가격을 보장하지 않는다.

## 서버와 데이터 보존

- V7: `product_watches`, `price_alerts` 추가.
- V8: `push_devices`, `alert_deliveries` 추가.
- 기존 V1~V6 마이그레이션은 수정하지 않았다.
- 가격 갱신·가격 이력·목표가 평가·알림 생성은 같은 트랜잭션이다. 알림 저장 실패 시 가격과 이력도 함께 취소된다.
- 출처 해시, 설정 버전, 설정 시각을 검사하므로 다른 출처나 설정 이전에 관측한 가격으로 알리지 않는다.
- 설정 버전의 유일 제약과 `armed` 상태로 설정당 중복 생성을 방지한다.
- 조회·수정·삭제·읽음 처리는 서버가 인증한 현재 계정으로 제한한다. 클라이언트가 사용자 ID를 지정하지 않는다.
- 계정이 바뀐 뒤 이전 응답이나 입력창의 정보가 적용되지 않도록 앱의 세션 세대를 검사한다.
- 알림에는 제품명·목표가·실제 관측 가격·출처·관측 시각을 저장한다. 제품의 현재 가격이 바뀌어도 과거 알림은 바뀌지 않는다.

## API

전체 계약은 `backend/openapi.yaml`에 포함했다. 아래 경로는 모두 Bearer 인증이 필요하다.

| 메서드·경로 | 용도 |
|---|---|
| `GET /api/v1/me/watches` | 내 관심 제품·목표가·설정 버전·대기 상태 |
| `PUT /api/v1/me/watches/{productId}` | `{targetPrice: 정수 또는 null, version: 정수}` 저장 |
| `DELETE /api/v1/me/watches/{productId}` | 관심 해제, 과거 알림 보존 |
| `GET /api/v1/me/alerts` | 최신 알림 100개 |
| `PUT /api/v1/me/alerts/{id}/read` | 내 알림 읽음 처리 |
| `GET /api/v1/me/push-status` | 서버 Firebase 클라이언트 초기화 여부 |
| `PUT /api/v1/me/push-device` | 등록된 FID와 플랫폼을 현재 계정에 연결 |
| `DELETE /api/v1/me/push-device` | 현재 계정의 기기 연결 해제 |

신규 관심 설정 버전은 0이다. 수정할 때는 조회한 버전을 보낸다. 충돌은 409이며 최신 정보를 다시 불러온 뒤 사용자가 저장한다. 불명확하게 실패한 저장 요청은 자동 재전송하지 않는다.

## Firebase 연결 상태

전용 프로젝트는 `pickwise-ebc42`이며 Android·iOS 앱의 식별자는 `kr.appsolute.pickwise`다. 다른 프로젝트의 구성 파일을 재사용하지 않았다.

사용자가 승인한 발송 전용 계정 `pickwise-push`에 `roles/firebasecloudmessaging.admin`을 부여하고 FCM API를 활성화했다. 비밀키는 `backend/.secrets/firebase-service-account.json`에 권한 600으로만 저장했다. `.secrets` 디렉터리는 700이다. Git과 Docker 빌드 컨텍스트에서 제외했으며 앱에 포함하지 않는다.

Android의 `google-services.json`, iOS의 `GoogleService-Info.plist`, 생성 가능한 `firebase_options.dart`도 Git에서 제외한다. 현재 앱은 Android·iOS 네이티브 구성 파일로 Firebase를 초기화한다. 별도 Mac에서 복제할 때는 해당 Firebase 프로젝트에서 구성 파일을 받아 동일한 위치에 두어야 한다. 공식 CLI로 다시 구성하려면 `sh backend/scripts/configure-firebase.sh`를 사용한다. Firebase CLI와 FlutterFire CLI가 필요하다.

현재 Mac의 Git 제외 `backend/.env`에는 다음 로컬 설정을 추가했다. 비밀번호와 기존 설정은 유지했다.

```dotenv
COMPOSE_FILE=compose.yaml:compose.firebase.yaml
PICKWISE_FIREBASE_CREDENTIALS=/절대/경로/backend/.secrets/firebase-service-account.json
```

`backend/compose.firebase.yaml`은 이 키를 `/run/secrets/firebase-service-account.json`에 읽기 전용으로 연결하고 서버 Firebase 발송을 활성화한다. 현재 API 컨테이너에서 키 읽기 가능 여부와 Firebase 초기화 성공을 확인했다. 이 설정은 개발용이며 공개 배포는 수행하지 않았다.

기본 구성만 사용할 환경은 `backend` 디렉터리에서 `docker compose -f compose.yaml up -d`를 실행한다. Firebase 연결을 유지하는 현재 Mac에서는 같은 디렉터리에서 `docker compose up -d`로 로컬 `.env`의 두 파일 구성을 사용한다. 키를 Git·앱·채팅으로 공유하지 않는다.

## 기기 푸시 동작과 한계

앱에서 **가격 알림함 → 이 기기에서 푸시 받기**를 선택할 때만 알림 권한을 요청한다. 로그인만으로 권한 팝업을 띄우지 않는다. 허용 후 FlutterFire의 `register()`와 `onRegistered`로 등록 완료된 Firebase Installation ID(FID)를 서버에 연결한다. 서버는 Admin SDK의 `setFid()`로 발송한다.

같은 FID는 마지막으로 등록한 계정 하나에만 연결한다. 계정당 최대 10개 기기다. 로그아웃 시 기기 등록 해제를 시도하고, 기기 해제가 실패하더라도 로그인 세션 폐기는 진행한다. 앱의 푸시 선택 상태는 계정별로 분리한다.

발송 작업은 30초마다 확인한다. 최근 하루의 읽지 않은 알림과 최근 30일 내 등록된 기기에만 전달을 시도한다. 기기별 발송 이력을 남기고 실패는 최소 5분 간격으로 최대 3회 시도한다. FCM 요청이 성공하고 DB 기록 전에 서버가 중단되면 같은 알림이 재전달될 가능성은 남으므로 정확히 한 번의 기기 도착을 보장하지 않는다. 알림함의 원본 기록은 설정당 한 번 생성된다.

잠금 화면에는 제품명·가격·계정 정보를 넣지 않고 새 가격 알림이 있다는 일반 문구만 보낸다. 열면 현재 로그인 계정의 알림함으로 이동한다. 앱 사용 중에는 안내 메시지와 알림함 진입 버튼을 표시한다.

**서버 Firebase 인증과 FCM의 `validate_only` 요청은 실제 성공했다. 서버와 같은 Java Admin SDK 9.12.0으로도 발송하지 않는 검증 요청의 성공을 확인했다. 이 검사는 기기로 알림을 보내지 않는다. 실제 기기 수신 검증은 아직 수행하지 않았다.**

iOS 원격 푸시는 Apple Developer 팀의 Push Notifications capability, 올바른 서명, APNs 인증 키의 Firebase 등록이 추가로 필요하다. 해당 Apple 계정·키는 현재 제공되지 않아 임의로 만들거나 다른 앱의 키를 재사용하지 않았다. iOS 빌드 성공과 원격 푸시 도착은 다른 검증이다. APNs 설정이 없어도 관심 제품과 앱 알림함은 사용할 수 있다.

## 검증 결과

| 검증 | 결과 |
|---|---|
| 실제 MySQL 기반 백엔드 전체 테스트 | 43개 성공, 실패·오류 0 |
| Flutter 전체 회귀 테스트 | 193개 성공, 기존 선택 실행 테스트 5개 건너뜀 |
| Flutter 분석 | 오류·경고 없음 |
| 목표가 입력·오류·계정 변경·작은 화면 테스트 | 6개 성공 |
| Android 디버그 APK | 빌드 성공 |
| iOS 시뮬레이터용 무서명 빌드 | 빌드 성공, 시뮬레이터 실행은 하지 않음 |
| 실제 HTTP와 외부 가격 | 격리된 테스트 DB에서 실제 234,710원 관측 → 목표가 알림 생성 성공 |
| 실제 HTTP 계정 분리 | 다른 계정의 알림 조회·읽음 차단, 관심 저장만 한 계정에는 알림 없음 |
| 재로그인 | 관심 제품·알림 유지 확인 |
| 관심 해제 | 과거 알림 보존 확인 |
| Firebase 실제 인증 | 전용 서비스 계정의 FCM `validate_only` 및 Java Admin SDK 검증 성공, 기기 발송 없음 |
| Docker Firebase 초기화 | 테스트 API에서 `configured=true` 확인 |
| 기존 서버 반영 | 8080 API만 재생성, MySQL 컨테이너 유지 |
| 기존 데이터 | 계정·제품 20개·비교 스냅샷·관리자 권한 보존 확인 |

자동 테스트에서 푸시 재시도·중복·계정 분리 검증에 사용하는 발송기는 테스트 대역이다. 실제 FCM 인증 검사는 별도로 수행했으며 실제 기기 수신과 혼동하지 않는다. 직접적인 Device Hub 조작은 하지 않았다. 커밋·푸시는 수행하지 않았다.

## 남은 직접 확인

1. 최신 앱을 다시 실행하여 제품 상세에서 목표가를 저장한다.
2. 마이페이지의 관심 제품과 가격 알림함을 확인한다.
3. Android는 Google Play 서비스가 있는 기기에서 알림 권한을 허용하고 실제 수신을 확인한다.
4. iOS는 APNs 키·팀 서명을 연결한 뒤 지원 기기에서 실제 수신을 확인한다.
